# Sermon Analyzer — Doctrine Report Output Spec

## Purpose

The doctrine report is the structured output produced from doctrine analysis.

It turns internal doctrine analysis into a clear, reviewable output for:

* doctrinal review
* sermon comparison against church doctrine
* downstream editing/reporting
* future book or archive workflows if needed

This report should be derived from structured doctrine analysis.
It should not be a freeform speculative summary.


---

## Core Principle

The doctrine report is:

* church-specific
* sermon-specific
* article-based
* structured first
* prose second

It must reflect the active `churchId` and the active doctrinal source for that church.


---

## Inputs

The doctrine report depends on:

* `churchId`
* `sermonId`
* doctrine analysis result
* active church profile
* active doctrinal source document
* optional sermon metadata
* optional sermon scripture references

It should not re-decide doctrine from scratch.
It should summarize and present the doctrine analysis output.


---

## Output Goals

The doctrine report should make it easy to answer:


1. which doctrinal articles were touched
2. how the sermon aligned with each article
3. what references supported the comparison
4. where ambiguity or conflict exists
5. what should be reviewed manually


---

## Output Types

The doctrine report should support two forms:

### 1. Structured report object

Machine-friendly, stable, reusable

### 2. Human-readable report

Readable summary for review

The structured object is primary.
The human-readable rendering is secondary.


---

## Structured Output Shape

```json
{
  "schemaVersion": "1.0.0",
  "artifactType": "DOCTRINE_REPORT",
  "churchId": "string",
  "sermonId": "string",
  "generatedAt": "ISO datetime",
  "sourceDoctrineDocument": {
    "name": "string",
    "path": "string"
  },
  "overallDoctrineAssessment": {
    "status": "ALIGNED",
    "summary": "string"
  },
  "matchedArticles": [
    {
      "articleId": "string",
      "title": "string",
      "matchStrength": "DIRECT",
      "alignment": "ALIGNED",
      "sensitivity": "NORMAL",
      "summary": "string",
      "supportingSermonReferences": [],
      "supportingDoctrineReferences": [],
      "notes": [],
      "reviewFlags": []
    }
  ],
  "unmatchedButRelevantDoctrineTopics": [],
  "reviewFlags": []
}
```


---

## Top-Level Fields

### `schemaVersion`

Schema version for the doctrine report artifact.

### `artifactType`

Fixed value:

```json
"DOCTRINE_REPORT"
```

### `churchId`

The active church context for the report.

### `sermonId`

The sermon being evaluated.

### `generatedAt`

When the report was produced.

### `sourceDoctrineDocument`

Reference to the doctrinal source used.

### `overallDoctrineAssessment`

Compact overall judgment for the sermon.

### `matchedArticles`

Main doctrinal findings by article.

### `unmatchedButRelevantDoctrineTopics`

Optional list for topics that seemed relevant but could not be matched strongly enough to a doctrine article.

### `reviewFlags`

Top-level report concerns.


---

## Overall Doctrine Assessment

This is the report-level summary.

Recommended allowed values:

* `ALIGNED`
* `MIXED`
* `AMBIGUOUS`
* `CONFLICT_PRESENT`
* `CONTRADICTION_PRESENT`

### Meaning

#### `ALIGNED`

No meaningful conflict detected across matched articles.

#### `MIXED`

Multiple matched articles with mixed outcomes, but not enough to label the whole sermon contradictory.

#### `AMBIGUOUS`

The doctrine signal is too unclear to summarize confidently.

#### `CONFLICT_PRESENT`

At least one meaningful doctrinal conflict is present.

#### `CONTRADICTION_PRESENT`

At least one clear doctrinal contradiction is present.


---

## Matched Article Object

Each doctrinal article touched by the sermon should be reported in a structured item.

```json
{
  "articleId": "string",
  "title": "string",
  "matchStrength": "DIRECT",
  "alignment": "ALIGNED",
  "sensitivity": "HIGH",
  "summary": "string",
  "supportingSermonReferences": [],
  "supportingDoctrineReferences": [],
  "notes": [],
  "reviewFlags": []
}
```


---

## Matched Article Fields

### `articleId`

Stable internal doctrinal article identifier.

### `title`

Human-readable doctrinal article title.

### `matchStrength`

Recommended MVP values:

* `DIRECT`
* `PARTIAL`
* `SECONDARY`

### `alignment`

Allowed values:

* `ALIGNED`
* `IMPLICIT`
* `AMBIGUOUS`
* `CONFLICT`
* `CONTRADICTION`

### `sensitivity`

Recommended MVP values:

* `NORMAL`
* `HIGH`

### `summary`

Short explanation of how the sermon relates to this doctrinal article.

### `supportingSermonReferences`

Scripture references used or clearly implied by the sermon for this doctrine area.

### `supportingDoctrineReferences`

Scripture references attached to the church's doctrinal article.

### `notes`

Short factual notes about the comparison.

### `reviewFlags`

Article-level review flags.


---

## Human-Readable Report Shape

The human-readable rendering should stay concise and structured.

Recommended sections:


1. report header
2. overall doctrine assessment
3. matched article summaries
4. review flags
5. unresolved / ambiguous items

### Example shape

* Church: FBCR
* Sermon: Blessed Are the Merciful
* Overall Doctrine Assessment: ALIGNED

Matched Articles:

* Sanctification — ALIGNED
* Security of the Saints — IMPLICIT
* Future Events — not meaningfully addressed

Review Flags:

* none

This human-readable layer can be markdown, but it should be derived from the structured report object.


---

## Reporting Rules

### 1. Only report meaningful matches

Do not flood the report with every doctrine article in the church profile.

### 2. Do not overstate certainty

If evidence is weak, use `AMBIGUOUS`.

### 3. Distinguish conflict from contradiction

Do not escalate conflict to contradiction unless the sermon clearly teaches against the doctrinal article.

### 4. Respect viewpoint classification

Mentioned-but-rejected views should not be treated as the sermon’s endorsed doctrine.

### 5. Include reference support when available

The report should show why a match or conflict was determined.


---

## Unmatched But Relevant Topics

This section is optional but useful.

Use it when:

* a sermon seems to touch a doctrine area
* but article matching confidence is too low
* or the sermon theme is adjacent to doctrine without enough evidence

Example values:

* `"possible sanctification theme"`
* `"possible family ethics theme"`
* `"possible eschatology reference"`

This helps preserve signal without overstating certainty.


---

## Recommended Top-Level Review Flags

Examples:

* `DOCTRINE_REPORT_LOW_CONFIDENCE`
* `MULTIPLE_HIGH_SENSITIVITY_TOPICS`
* `POTENTIAL_DOCTRINAL_CONFLICT`
* `POTENTIAL_DOCTRINAL_CONTRADICTION`
* `MISSING_SUPPORTING_REFERENCES`
* `VIEWPOINT_INTERPRETATION_REVIEW`

These are report-level flags, not article-only flags.


---

## Recommended Article-Level Review Flags

Examples:

* `ARTICLE_MATCH_LOW_CONFIDENCE`
* `ALIGNMENT_AMBIGUOUS`
* `HIGH_SENSITIVITY_ARTICLE`
* `SCRIPTURE_REFERENCE_MISMATCH`
* `POTENTIAL_CONTRADICTION`
* `ENDORSEMENT_UNCLEAR`


---

## What the Doctrine Report Should Not Do

Do not:

* restate the full church doctrinal document
* dump every article whether relevant or not
* speculate beyond the sermon evidence
* flatten church doctrine into one generic paragraph
* hide ambiguity
* ignore `churchId`


---

## Relationship to Other Artifacts

### Depends on

* doctrine analysis output
* church profile
* doctrinal source document

### Used by

* human review
* downstream output generation
* future archival/reporting workflows

The doctrine report is not the doctrinal source.
It is an analysis output derived from that source.


---

## Definition of Done

The doctrine report output is working when it can:


1. produce a structured doctrine report object
2. summarize overall doctrinal assessment
3. report matched doctrinal articles only
4. show alignment per article
5. include scripture support comparison where available
6. clearly flag ambiguity, conflict, or contradiction
7. support a readable human-facing rendering


---

## Summary

The doctrine report is the structured presentation layer for doctrine analysis.

It should be:

* article-based
* church-specific
* reference-aware
* review-friendly
* derived from structured analysis, not freeform guesswork
