# Sermon Analyzer — Transcript POC

## Purpose

The Transcript POC is the first implementation target.

Its job is simple:

**take one video/media URL, transcribe it, and write a transcript file**

This is a proof of concept for the core technical path.

It is not trying to solve the full Sermon Analyzer architecture yet.


---

## Why This Comes First

Do not build a cart until you have a horse.

Before building:

* shared processors
* registries
* discovery workflows
* backfill automation
* doctrine analysis
* output generation

We first need to prove that the stack can reliably do:

**URL -> media/audio -> transcription -> transcript file**

If that does not work, everything else is premature.


---

## Goal

Prove that the tech stack works end-to-end for one sermon source.

The first working success is:


1. manually start workflow
2. provide one hardcoded test URL
3. fetch media or audio
4. transcribe successfully
5. save transcript output file
6. inspect transcript quality


---

## Scope

### In scope

* manual workflow start
* one hardcoded test sermon URL
* one transcription provider
* media acquisition
* audio preparation if needed
* transcription
* save transcript file locally
* basic success/failure result

### Out of scope

* shared processor
* canonical transcript schema enforcement
* registry/state tracking
* transcript reuse
* sermon identity rules
* discovery
* scheduling
* doctrine analysis
* output generation
* full series handling
* historical lookback automation


---

## Success Criteria

The POC is successful if:


1. a valid sermon media URL can be processed
2. the workflow can produce transcript text
3. the transcript is saved to a local file
4. the saved file is readable
5. the workflow can be rerun manually with another test URL

Nice to have, but not required for POC:

* JSON transcript output
* timestamps
* segments
* metadata enrichment


---

## Core Principle

The Transcript POC is the **horse**.

Everything else is downstream or upstream of this.

### Upstream later

* source discovery
* backlog automation
* metadata capture
* series handling

### Downstream later

* transcript normalization
* analysis
* doctrine detection
* output generation


---

## Testing Strategy

Testing should also produce useful assets.

If the POC works, use testing runs on backlog sermons to generate transcript files.

That means testing can:

* validate multiple sources
* build useful transcript inventory
* reduce later need for complex historical lookback workflows

Because of that, complex lookback / older-series retrieval can move later, likely to a future version such as **v4.0**.

## Required Tech Stack Pieces

These must work before the POC can succeed:

* n8n running locally
* one working transcription provider/API
* credentials configured
* ffmpeg available if video/audio conversion is needed
* local writable output path
* one known-good sermon media URL for testing


---

## Minimal Workflow


1. Manual Trigger
2. Set Hardcoded Test URL
3. Download or access media
4. Prepare audio if needed
5. Send to transcription provider
6. Receive transcript
7. Save transcript to file
8. Return success or failure


---

## Output

Minimum required output:

* one transcript text file

Optional for early testing:

* raw provider JSON response file

POC does not require:

* canonical transcript artifact
* registry record
* version tracking
* series metadata


---

## Definition of Done

The Transcript POC is done when:


1. one sermon video/audio URL is successfully transcribed
2. transcript text is written to disk
3. result can be manually reviewed
4. the process can be repeated on additional backlog sermons


---

## Notes

The POC should stay intentionally small.

Do not overbuild:

* no registry yet
* no reuse logic yet
* no shared processor yet
* no discovery logic yet

Once this works, then build outward:

* downstream into analysis
* upstream into better acquisition and backlog handling
