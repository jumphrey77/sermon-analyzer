# Sermon Analyzer — Workflow Spec

## Purpose

This document defines the workflow architecture for Sermon Analyzer.

It also defines the **development order** for implementation.

These are not the same thing:

* **final architecture** = where the system is going
* **development order** = what gets built first

The system should be built from the core proof of concept outward.


---

## Core Principle

Do not build a cart until you have a horse.

The first thing that must work is:

**video/media URL -> transcription -> transcript file**

If that does not work reliably, then building:

* shared processors
* registries
* discovery workflows
* backfill automation
* doctrine analysis
* output generation

is premature.


---

## Development Order

### Phase 1 — Transcript POC

This is the first implementation target.

Goal:

* manually run one workflow
* provide one hardcoded test URL
* fetch media or audio
* transcribe successfully
* save transcript output file

This proves the tech stack works end-to-end.

### Phase 2 — Transcript Hardening

After the POC works:

* improve file naming
* define canonical transcript artifact
* normalize transcript format
* improve error handling
* optionally save raw provider response
* optionally add minimal metadata

### Phase 3 — Backlog Processing During Testing

Once transcription works, use testing runs on backlog sermons to generate transcript files.

This has two purposes:

* validate the workflow on multiple real sermon sources
* build useful transcript inventory while testing

This reduces pressure to build complex historical lookback early.

### Phase 4 — Downstream Processing

Once transcript artifacts exist, build downstream logic:

* structure analysis
* doctrine/reference analysis
* outputs

This is easier because the transcript becomes a stable input.

### Phase 5 — Upstream Hardening

After transcript generation is proven and downstream work begins, build upstream logic:

* better metadata capture
* better source handling
* source resolution
* manual backfill convenience
* transcript reuse
* minimal registry/state

### Phase 6 — Shared Sermon Processor

Once the core pieces are proven separately, combine them into the reusable shared sermon processor.

### Phase 7 — Discovery / Scheduling / Historical Retrieval

Only after the core is proven should the system add:

* scheduled discovery
* historical backfill automation
* mid-series recovery
* deeper source crawling

Complex historical lookback can move later, potentially to a future version such as **v4.0**.


---

## Final Workflow Architecture

The final workflow architecture still centers on one shared reusable processor.

### Final workflows


1. Config Intake
2. Historical Backfill
3. Scheduled Discovery
4. Single Sermon
5. Shared Sermon Processor

Rule:
All parent workflows must call the Shared Sermon Processor.
They must not duplicate sermon processing logic.


---

## Shared Sermon Processor

The Shared Sermon Processor is the long-term reusable workflow core.

Its major stages are:


1. Ingestion
2. Transcription
3. Analysis
4. Output Generation
5. State Update

However, this is the **target architecture**, not the first implementation step.

The first implementation step is still the Transcript POC.


---

## Workflow Relationships

### POC-first view

Build order should follow this dependency chain:


1. Transcript POC
2. Transcript hardening
3. Transcript backlog accumulation during testing
4. Analysis
5. Outputs
6. Shared processor
7. Discovery / scheduling / historical automation

### Final architecture view

Once mature, the system flows like this:

* parent workflow selects sermon
* parent workflow calls Shared Sermon Processor
* shared processor handles sermon processing
* outputs and state are updated centrally

## Workflow Definitions

### Config Intake

Purpose:

* receive or load config
* validate config
* prepare workflow context

Status:

* architecture-level workflow
* not first implementation target

### Historical Backfill

Purpose:

* process a list of previously identified sermons

MVP preference:

* explicit sermon lists
* avoid deep crawling early

Status:

* later workflow
* not required for Transcript POC

### Scheduled Discovery

Purpose:

* look for newly available sermons on schedule

MVP preference:

* simple Monday schedule
* defined lookback window
* explicit and predictable behavior

Status:

* later workflow
* not required for Transcript POC

### Single Sermon

Purpose:

* manually process one sermon from a provided input

This will eventually call the Shared Sermon Processor.

Status:

* later than Transcript POC
* may evolve from the POC workflow

### Shared Sermon Processor

Purpose:

* one reusable processing core for all sermon-processing workflows

Status:

* target architecture
* not first build step


---

## POC Workflow Definition

### Transcript POC

Purpose:

* manually start workflow
* use one hardcoded test sermon URL
* download or access media
* prepare audio if needed
* transcribe
* save transcript file
* return success or failure

This is the first implementation workflow.

It does not require:

* registry
* reuse logic
* canonical transcript schema enforcement
* discovery
* scheduling
* outputs
* doctrine analysis


---

## Workflow Design Rules

### 1. No Duplication

Final architecture uses one Shared Sermon Processor.

### 2. Simplicity First

Prefer explicit workflows and narrow responsibility.

### 3. Determinism

Same input should produce the same output behavior where possible.

### 4. Build in dependency order

Do not build orchestration before proving the core transcription path.

### 5. Use testing to create assets

Backlog testing should produce useful transcript files, not throwaway work.


---

## Backlog Strategy

Testing should be used to generate real transcript assets from older sermons.

This means backlog processing can begin during testing instead of waiting for a full automated backfill workflow.

As a result:

* transcript inventory grows early
* downstream analysis can begin sooner
* complex historical recovery can be deferred
* “starting in the middle of a series” becomes less urgent

Complex historical lookback is therefore a later concern, not an immediate one.

## Summary

The final system still aims for a shared reusable processor.

But implementation should begin with the smallest proof of concept:

**URL -> transcription -> transcript file**

Build the horse first.
Then build the cart around it.
